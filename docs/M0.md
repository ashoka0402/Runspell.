# M0: shared contracts and feasibility

Date: 19 November 2026

Scope: [M0 in the roadmap](../ROADMAP.md#m0--contracts-and-feasibility).

## Status and boundaries

The offline contract and canvas gates are implemented and verified. Full M0 remains open because its live provider gate is intentionally pending.

M0 establishes executable contracts and an isolated canvas compatibility spike. It does not implement the API, managed authentication, PostgreSQL persistence, real model generation, or an automation runner.

Provider checks are offline at the user's explicit direction. No Trigger.dev or Steel tasks, sessions, login attempts, paid resources, schedules, or deployments may be started as part of this offline work. A passing fixture or local browser test is not evidence of live provider compatibility.

## Contract decisions

### Action and workflow boundaries

- Capabilities are registered by action type and version, with typed configuration and input/output schemas.
- Each supported action declares its runtime, required scopes, side-effect class, limits, retry policy, and evidence policy.
- A workflow graph has stable node/edge IDs and schema version, with explicit references to earlier outputs. Canvas coordinates are presentation data.
- Compilation validates supported action versions, graph structure, connection policy, references, and applicable limits. It returns a plan/validation result, never executable AI code.
- The invoice fixture uses supported actions only. It does not claim that a website connector, connected account, approval service, or API integration has been implemented.
- This milestone supplies validation contracts. Actual authorization, credential access, policy enforcement at execution time, and private artifacts require the backend and runner milestones.

Budget values in the fixture catalog are illustrative validation caps, not measured provider prices, account limits, or an authorization to spend. Production policy values must be based on account capacity and measured behavior before live execution.

### Drafts, patches, generations, and streaming

- A candidate patch targets a specific draft revision. Conflicts reject instead of overwriting accepted work.
- Applying a patch affects a draft, never an active immutable workflow version.
- Events carry a generation identity, sequence/cursor, event type, and draft revision. Stable event identity permits duplicate detection.
- Replay must not silently skip missing events or accept another generation's changes. A gap requires replay from the retained cursor or a validated authoritative snapshot.
- A refresh reconstructs the accepted graph from snapshot plus ordered events; animation completion is not a persistence acknowledgement.
- Generation failure or interruption leaves the last accepted draft available for editing. Readiness means the draft passes the defined checks; it does not mean execution succeeded.
- Snapshots retain typed clarification questions, failure messages, and warnings so a reconnect can explain the current state without decoding internal duplicate-detection records. Lifecycle changes clear stale questions/errors; warnings remain available for review.
- The pure projector and fixtures are exercised offline here. Durable database writes, authenticated SSE transport, retention, and `Last-Event-ID` handling on a real server arrive with M2/M3.

Current helper contract:

| Export | Behavior |
| --- | --- |
| `compileWorkflow(input, policy)` | Returns the validated workflow, topological order, and missing connection requirements; rejects unsupported/invalid candidates |
| `createDraftSnapshot(generationId, workflow, revision)` | Starts a generation at event cursor zero while preserving the supplied accepted draft revision |
| `applyDraftPatch(snapshot, { expectedRevision, workflow }, policy)` | Validates a complete candidate replacement and returns the next draft revision without mutating the original |
| `replayDraftEvents(snapshot, events, policy)` | Applies the next ordered events, ignores verifiably identical duplicates, rejects conflicts/gaps, and returns the next snapshot |

The patch response is an updated authoritative snapshot. A client accepting a patch replaces its local projection from that snapshot; it must not keep applying stale generation changes. Starting a new generation preserves the accepted draft revision. Node/edge mutations advance the draft revision; status-only events advance the sequence but keep the revision unchanged. Event IDs are `<generationId>:<sequence>`.

The first catalog contains six invoice-oriented actions. Definitions use schema/action version 1, bounded acyclic graphs, simple true/false branches, and top-level scalar output references whose source is guaranteed on the consumer's path. Unrestricted graphs, general selectors/code execution, dynamic expression evaluation, nested reference paths, loops, and parallel execution are not implemented. JSON Schema exports describe structure; compiler/Zod checks also enforce graph, scope, and URL semantics.

### Four test modes

| Mode | Permitted behavior | User-visible meaning |
| --- | --- | --- |
| Schema validation | Parse and compile definitions only | Definition checks passed/failed; nothing executed |
| Mocked execution | Resolve controlled fixtures without provider calls | Simulated results; no external success claimed |
| Read-only real execution | Explicitly authorized reads against configured accounts | Observations from real systems; no writes permitted |
| Controlled write test | Explicitly authorized writes against controlled test accounts with declared effects | Real test actions with recorded outcome/uncertainty |

M0's implemented checks use the first two modes. Opening the local compatibility page in Chrome is browser UI testing, not a Steel browser-automation run. Test-mode labels and schema fields are not security boundaries by themselves: the future runner must enforce allowed actions and destinations.

### Runs, evidence, approval, and recovery

- Distinguish accepted/queued/running work, waiting for approval, cancellation requested, terminal results, expiry/rejection, and `needs_attention`.
- An observed task result, a verified external business outcome, and an unknown external outcome are separate facts.
- An approval is bound to action details and version. Only an authorized, pending, unexpired decision can resume its action, through durable decision/signal recovery.
- A cancellation request does not prove that a provider stopped or that an earlier external write was reversed.
- An ambiguous state-changing action requires reconciliation; it cannot be retried merely because a task or AI planner recommends it.
- Long waits must not retain browser sessions by default. Runtime leases, release, reconciliation, and budget enforcement are prerequisites for live execution.

## Canvas compatibility scope

The opt-in workspace route is `/app/#/m0`. Its graph is a validated local fixture. The surrounding app remains plain HTML/CSS/JavaScript.

The spike checks:

- Isolated React mounting and unmounting within the existing workspace.
- Scoped React Flow styles, without overwriting legacy app styles.
- GSAP cleanup and reduced-motion behavior.
- Route-away/back behavior and repeated mounting.
- Keyboard interaction and usable controls.
- Preservation of the existing `brisko.workflow.drafts` storage value.
- Clear offline/fixture labels and absence of external execution controls.

This is a compatibility page, not M1 Prompt Studio or a finished workflow authoring experience.

## Local verification

From the repository root:

```powershell
npm ci
npm run typecheck
npm test
npm run build
npm run test:browser
py -m unittest discover -s tests -v
```

The browser suite uses installed Google Chrome through Playwright. It starts a dedicated public-assets preview on loopback port 8001. It requires Python's `py` launcher and Chrome on this Windows setup. No provider account is needed.

To open the fixture manually after building:

```powershell
npm run preview
```

Visit [the M0 compatibility page](http://localhost:8000/app/#/m0). If port 8000 is already serving this repository, reuse that server. The original landing page and workspace continue to work without a canvas build; the new route needs its generated bundle.

## Live provider gate: pending

When separately authorized, use test credentials supplied through secure environment configuration and an agreed spending bound. Verify the following rather than inferring success from mocks:

| Check | Required evidence |
| --- | --- |
| Trigger.dev to Steel to Playwright | Actual task ID, session ID, successful controlled navigation, and terminal task state |
| Login/profile lifecycle | Controlled login, confirmed profile save/readiness, fresh-session authentication verification, and expired-login behavior |
| Cleanup and task termination | Explicit release on success/failure; orphan cleanup after forced worker termination; measured lifetime within hard/inactivity bounds |
| Viewer/handoff access | Actual authorization model, least access, time limits, revocation, and profile/session exclusivity |
| Network restrictions | Proven handling of prohibited URLs, redirects, DNS/private-address cases, and browser subrequests |
| Budget and capacity | Current account limits, deliberate task/session timeouts, no unintended retries/proxies/CAPTCHA costs, and measured usage |

Unknown viewer/network controls block exposing unrestricted browser sessions to users. The user has not authorized this live gate, and no live success is claimed.
